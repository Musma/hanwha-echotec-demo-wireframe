상태 UI 가이드
화면을 그릴 때 함께 그려야 하는 것 — Loading · Empty · Error

우리가 시안으로 그리는 화면은 대부분 데이터가 잘 들어온 상태(Happy path) 하나입니다. 그런데 사용자가 실제로 만나는 화면의 상당수는 기다리는 중이거나, 비어 있거나, 실패한 화면입니다. 이 문서는 그 세 화면을 디자이너가 무엇을 기준으로 판단하고, 무엇을 산출물로 넘겨야 하는지를 정리한 것입니다.

01. 사용자는 기다림을 이렇게 느낀다

로딩 UI의 목적은 "속도를 빠르게" 하는 게 아니라 불확실성을 없애는 것입니다. 사용자가 불안해지는 순간은 느릴 때가 아니라 무슨 일이 일어나는지 모를 때입니다.

사용자가 불안해지는 신호
  • 눌렀는데 아무 반응이 없다 → 다시 누른다
  • 화면이 통째로 하얘졌다 → 실패했다고 판단
  • 인디케이터가 번쩍하고 사라졌다 → 오류로 착각
  • 언제 끝나는지 모른다 → 새로고침
체감 시간을 줄이는 방법
  • 결과의 형태를 미리 보여준다 (스켈레톤)
  • 기다리는 동안 다른 걸 만질 수 있게 둔다
  • 진행 단계를 말로 알려준다
  • 기다림을 아예 없앤다 (즉시 반영 후 정정)
현장 환경을 전제로 판단합니다. 야외 직사광선, 장갑 착용, 불안정한 무선망. 화면이 조금 느린 것보다, 무엇이 진행 중인지 모르는 것이 훨씬 큰 사고로 이어집니다.

02. 화면 하나에 그려야 할 상태 세트

시안 산출물의 최소 단위는 화면 1장이 아니라 상태 4장입니다. 데이터를 그리는 영역이 있는 화면은 예외 없이 아래를 함께 만듭니다.

여기에 더해, 데이터가 많은 경우 / 글자가 아주 긴 경우도 함께 확인합니다. 지번명이 3줄로 늘어나거나 목록이 500건일 때 레이아웃이 무너지는지는 시안 단계에서만 잡을 수 있습니다.

가장 흔한 사고 · 상태 시안을 안 넘기면 개발자가 임의로 만듭니다. 그 결과 화면마다 로딩 표현이 달라지고, 빈 화면은 "데이터 없음" 한 줄이 되며, 오류는 서버 메시지가 그대로 노출됩니다. 이건 개발 이슈가 아니라 디자인 누락입니다.

03. 로딩 패턴 고르기 — 세 가지 질문

Q1얼마나 걸리나?
예상 소요 그려야 할 것
~1초아무것도 그리지 않는다. 버튼 pressed 상태로 충분
1~5초스켈레톤(최초) 또는 스피너(갱신)
5~30초프로그레스 + 진행 단계 문구 + 취소 버튼
30초 초과기다리게 하지 않는다. "완료되면 알림" 안내 후 화면 해제
소요 시간은 추측이 아니라 개발팀에 물어봅니다. "이 조회 보통 몇 초 걸려요?" 한 마디로 패턴이 정해집니다.
Q2기다리는 동안 사용자가 할 일이 남아 있나?

남아 있으면 그 부분은 절대 덮지 않습니다. 차단 범위는 "예쁨"이 아니라 "지금 무의미해진 영역"으로 정합니다.

차단 범위 쓰는 경우 물류Twin 사례
화면 전체앱 전체가 멈춰야 할 때만. 남발 금지로그인, 로그아웃
영역(섹션)테이블·맵만 갱신. 필터는 계속 만질 수 있어야 함지번 목록 조회
컨트롤 하나버튼·셀렉트 범위저장 버튼

Q3끝이 언제인지 보여줄 수 있나?

퍼센트를 안다 → 프로그레스 바. 단계만 안다 → "2/3 지번 매핑 중" 스텝 표기. 아무것도 모른다 → 스피너.
10초를 넘는 작업에서 스피너만 도는 것과 단계를 말해주는 것은 체감 차이가 매우 큽니다. 가능하면 단계를 만들어 달라고 요청하세요.

3-1. 스켈레톤 vs 스피너 — 판단 기준

스켈레톤 — 3가지 모두 맞을 때
  • 화면에 처음 들어온 순간이다
  • 결과가 어떤 모양일지 우리가 안다
  • 1초 이상 걸린다
스피너 — 다음 경우
  • 이미 데이터가 떠 있는데 다시 조회한다
  • 결과 모양을 예측할 수 없다
  • 영역이 좁다 (버튼, 셀, 아이콘)
시안에서 자주 나오는 실수
  • 결과와 모양이 다른 스켈레톤 — 실제 데이터가 뜰 때 레이아웃이 튄다. 스켈레톤은 실제 컴포넌트를 복사해서 회색으로 바꾼 것이어야 한다
  • 재조회할 때도 스켈레톤 — 보고 있던 데이터가 사라진다. 기존 데이터를 흐리게(불투명도 50%) 두고 스피너를 올리는 것이 정답
  • 화려한 shimmer 애니메이션 — 업무 화면에서는 산만하다. 느린 pulse까지만
  • 조회할 때마다 화면 전체 딤 — 필터를 연속으로 바꾸는 작업이 매우 답답해진다
깜빡임 방지 — 시안에는 안 보이지만 반드시 전달할 규칙
400ms 지연 후 등장 · 빠른 응답에는 인디케이터가 아예 뜨지 않게 한다.
한번 떴으면 500ms 유지 · 번쩍이고 사라지면 오류처럼 보인다.
두 규칙이 없으면 아무리 잘 그린 로딩 UI도 실제 화면에서는 깜빡임으로만 보입니다. 핸드오프 노트에 꼭 적으세요.

05. Empty — 비어 있는 화면 4유형

"데이터 없음" 한 줄로 끝내지 않습니다. 비어 있는 이유가 다르면 사용자가 해야 할 다음 행동도 다릅니다. 유형을 먼저 구분한 뒤 문구와 버튼을 정합니다.

유형 언제 문구 · 다음 행동
최초 빈 상태아직 아무도 등록하지 않음"등록된 논리지번이 없습니다" + 등록 버튼(강조). 4유형 중 유일하게 CTA를 오렌지로
검색 결과 없음필터·검색 결과 0건"검색 조건에 맞는 지번이 없습니다" + 조건 초기화. 적용 중인 조건을 그대로 보여준다 — 뭘 바꿔야 할지 알 수 있게
조회 전조건을 넣어야 결과가 나오는 화면"조회 조건을 선택한 뒤 조회 버튼을 눌러 주세요". 오류처럼 보이지 않게 중립 톤·아이콘
권한 없음볼 수 있는 계정이 아님"열람 권한이 없습니다. 관리자에게 문의해 주세요" + 문의 경로. 재시도 버튼을 넣지 않는다 — 눌러도 달라지지 않음
등록된 논리지번이 없습니다
상위 물리지번을 선택해 논리지번을 추가할 수 있습니다.
검색 조건에 맞는 지번이 없습니다
구역 A · 상태 진행중 · 2026-07-01 ~ 07-28
그리기 규격 · 영역 최소 높이 웹 240px / 모바일 200px — 데이터가 있을 때와 높이가 비슷해야 화면이 튀지 않습니다. 아이콘 48px #C6C6C6, 제목 14px Bold, 설명 12px, 중앙 정렬. 일러스트·이모지는 쓰지 않습니다.

06. Error — 실패를 알리는 6단계

오류 화면은 영향 범위에 맞춰 크기를 정합니다. 작은 실패에 큰 모달을 띄우면 사용자는 곧 오류를 읽지 않게 됩니다. 어떤 방식이든 무엇이 실패했는지 · 왜 · 지금 뭘 하면 되는지 세 가지는 항상 담습니다.

6-1. 자주 만나는 실패 상황별 화면

상황 화면 처리
결과가 0건오류 아님. Empty로 분기 — 빨간색·경고 아이콘을 쓰지 않는다
입력값이 틀림필드 인라인. 어떤 형식이어야 하는지 예시를 함께 — "예) A-12"
로그인 만료모달로 알리고 로그인으로. 작성 중이던 내용은 보존하고 돌아왔을 때 복원
권한 없음Empty(권한) 유형. 재시도 버튼 없음, 문의 경로 제공
없는 데이터로 진입전체 화면 오류 + "목록으로 돌아가기". 뒤로가기만 남기지 않는다
다른 사람이 먼저 수정충돌 모달 — "다른 사용자가 먼저 수정했습니다" + 최신 내용 보기 / 내 내용으로 덮어쓰기 선택. 여러 명이 같은 지번을 만지는 업무라 반드시 설계
서버 오류영역 오류 + 다시 시도. 오류코드를 작게 병기 — 현장에서 전화로 문의할 때 필요
응답이 아주 느림조회는 조용히 재시도 후 오류. 저장·배차 같은 쓰기 작업은 자동 재시도하지 않는다 — 중복 생성 위험
현장 네트워크 끊김모바일 상단 고정 배너 "오프라인 · 연결되면 자동 전송". 입력한 내용은 보관했다가 자동 전송
오류 문구 작성 규칙
  • 개발 용어·서버 원문 메시지를 그대로 노출하지 않는다. 사람 말로 옮기고 오류코드만 작게 남긴다
  • 사용자를 탓하지 않는다 — "잘못 입력했습니다" → "지번코드 형식이 올바르지 않습니다. 예) A-12"
  • "오류가 발생했습니다" 단독 금지 — 무엇이 실패했는지 대상을 밝힌다
  • 되돌릴 수 없는 작업(삭제·배차 확정)의 실패는 토스트가 아니라 모달로 확실히 알린다
  • 느낌표·이모지를 쓰지 않는다. 현장 업무 시스템의 신뢰도를 떨어뜨린다

12-1. 깜빡임 방지 · 성공 알림 · 접근성 (2026.07.28 보완)

가이드 항목목업 구현
400ms 지연 등장 · 500ms 최소 유지 (§03, §10)재조회·저장 인디케이터에 적용. 400ms 안에 끝나면 아예 뜨지 않고, 떴으면 500ms를 채우고 사라집니다. 최초 진입 스켈레톤은 대체할 내용이 없어 즉시 노출(깜빡임 위험 없음).
중복 실행 방지 (§10)스피너 등장 여부와 무관하게 저장·삭제는 1회만 실행됩니다(지연 400ms 구간의 연타 포함).
저장·삭제 성공 문구 (§09)토스트 — “저장되었습니다” 4초 · “삭제되었습니다” 5초 + 실행 취소 버튼
접근성 (§10)화면당 aria-live="polite" 안내 영역이 로딩·저장·업로드 진행률·토스트를 읽어 줍니다. 모션 최소화 설정 시 스피너·pulse·진행바 회전 정지.
응답 속도 검증Tweaks 패널 상태 UI › 응답 속도 — 빠름(0.25×) / 보통 / 느림(2.5×). 빠름으로 두면 400ms 지연 등장 규칙이 실제로 동작하는 것을 확인할 수 있습니다.

남은 항목 — 조회 실패·서버 오류 토스트는 목업 동작에 넣지 않았습니다(정적 시안으로 대체). 실 API 연동 시 §07 매트릭스의 Error 열을 그대로 붙이면 됩니다.
